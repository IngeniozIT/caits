# Changelog

The changes of each version of CAITS, the newest first. A version is a git tag, and a version of the package `@ingenioz-it/caits` on npm: `npx @ingenioz-it/caits@<version> init my-app`.

## 0.8.1

### Packages

- A new project has no vulnerability, and warns of nothing, from `npm install` to `npm run check`. Before, `npm install` reported 21 vulnerabilities (20 moderate, 1 high) and warned of install scripts. `init` writes two values more in package.json:
  - `overrides`: the tools ask for versions that have advisories, which their later versions fix. ESLint, typescript-eslint, Stryker and glob ask for minimatch 10, @marko/run for glob 13, and Stryker, through typed-rest-client, for qs 6.15.1: npm installs minimatch 11, glob 14 and qs 6.17 in their place.
  - `allowScripts`: npm 11.20 runs the install scripts of a package only when the project allows them, and warns about the others. esbuild and @parcel/watcher work without theirs: CAITS denies them, and npm runs no code of theirs as it installs.
- `caits update` gives the `npm pkg set` command that adds to package.json the values that CAITS adds and that it lacks, as these two, and tells an override whose version differs from that of CAITS with the other versions. In a project, run `npx caits update`, then the commands that it gives, then `npm install`.
- CAITS suggests the last version of each tool: happy-dom 21.0.4 (which fixes two advisories, one high: it loads no stylesheet and no iframe by default), ESLint 10.14, typescript-eslint 8.72, Vite 8.3.5, Vitest 5.0.5, @marko/run 0.11.16, Marko 6.4.7, @marko/compiler 5.42.13, Playwright 1.64.1, @vitest/coverage-v8 5.0.5, Sass 1.107 and @types/node 26.6.6. TypeScript stays at 6: typescript-eslint takes no version from 6.1 on, and @marko/type-check uses its own TypeScript 6. CAITS needs Vite 8.1 at least, and uses magic-string 1.

### Development server

- `caits dev` gives the port of HMR in `server.ws`, which Vite reads since its version 8.1, and still in `server.hmr`, which @marko/run reads before it looks for a free port. The configuration of CAITS (quality/caits/vite.ts) has no `server` any more: the kernel plugin tells the development server the files that it does not watch, the reports and the sandbox of the mutation tests. Before, Vite warned at each start that `server.hmr.port` is deprecated, as it merged the port into the `server` of the configuration. A project whose quality/vite.config.ts gives a `server` brings the warning back: give it from a plugin, in its `config` hook.

### Tests

- The files that @marko/run generates, as its router, have no source map. Vitest replaces `import.meta.env` in them, with a map to a file that is not on the disk, and Vite warned at the first run of the tests, and after each change: `Sourcemap for ".../__marko-run__router.js" points to missing source files`.

### Mutation tests

- Stryker no longer warns of static mutants, the changes of code that runs as a module loads: CAITS tests them all, and `caits mutation` counts as killed one whose code throws as soon as a test loads it.
- Stryker no longer warns of a pattern of `mutate` that matches no file, as `!src/frontend/*/di.ts` in a project without a frontend context, or `src/**/*.ts` in a new project: the defaults of CAITS keep the patterns that match files of the project. Without any, as in a new project, `caits mutation` runs no Stryker, which warned that it found no file to mutate, and passes.

## 0.8.0

### Kernel

- The server of an app boots its backend and stops it. CAITS gives an adapter of @marko/run, `adapter` from `@ingenioz-it/caits/vite`, which quality/caits/vite.ts gives to the plugin of @marko/run: `npm run build` builds the server of `npm start` from the entry of CAITS, and `caits dev` serves the app in a server of its own. Both boot the backend before they serve, with the bindings of the di.ts of the contexts, and start its timer controllers. On SIGTERM (`docker stop`) or SIGINT (Ctrl+C), they serve no new request, end the feeds, stop the timers, let the requests, the turns of the timers and the reactions to the events that run end for up to 10 s, then give the turns and the reactions that still run one more second, once their signal aborted, and report them, release what the containers built, and end with 0. Docker kills the server 10 s after `docker stop` by default, as long as the grace: an app whose requests can last more than a few seconds sets `stop_grace_period` in its compose above the grace, one second more and the time to release what it built. A second signal, a second or more after the first, ends them at once; a signal that comes twice at once, as when npm passes Ctrl+C on to the server, counts once. Before, Node ended at once on SIGTERM and cut the requests that ran, and `caits dev` stopped without a word on Ctrl+C. `caits dev` boots the backend again when a module that the backend imports changes, after it stopped the old one: two backends never run at once; it does not wait for the requests that run. A request that comes meanwhile waits for the new backend, and a boot that fails then is reported, without stopping `caits dev`; a first boot that fails, or a port in use, ends `caits dev` with its error. Once the server closes, the connection of a request that ends closes: a client would keep it open for a few seconds, which the close would wait for. A request that still comes on a connection that serves another gets a 503, which closes the connection: before, it could start a second backend, which nothing stopped. In a project, run `npx caits update`.
- A timer controller sends an input DTO at each turn of a timer, as an HTTP controller does for a request: `<use-case>.timer.controller.ts` exports a class that extends `TimerController<InputDto>`, from `@ingenioz-it/caits/messaging/TimerController`, with `every`, in milliseconds, and `toDto()`. The kernel runs it while the server runs, each turn in a request of its own, and skips a turn while the last one runs: an error of a turn is reported, and the next turn comes anyway. A rhythm that is not a number of milliseconds above 0, up to 2147483647 (24 days), is refused when the server starts, before any timer runs: Node runs a longer one every millisecond. `controller-extends-controller` takes it. Its presentation test runs one turn: `presentationScenario(app).givenTheTimer(…).expectItToSend(…).givenTheApplicationReplies(…).expectTheTurnToRunEvery(…)`.
- A stream controller answers with server-sent events, before its handler ends: `<use-case>.stream.controller.ts` exports a class that extends `StreamController<InputDto, OutputDto>`, from `@ingenioz-it/caits/messaging/StreamController`. It writes the events that the handler publishes, as it publishes them (`toChunk`), then its output (`toOutputChunk`), which ends the stream; with `follows = "context"`, it writes the output first, the state at the start, then the events of every request of its context, until the client leaves. An event that came while the handler read the state may be in it already: `stateHolds(state, event)` says so, and the feed does not write it again; it writes each event that comes after the state. A feed ends when the backend stops, at a `docker stop` or when `caits dev` reloads the code: the events of its context end (`ContextEvents.signal` aborts), and its client connects again, to the next backend. A stream of a request goes on, as any request that the server lets end. An `EventSource` connects again to any stream that ends, with the same `GET`: a feed gives its state again, but a stream of a request would run its use case again and again, so its client closes it at the last event, or the API takes `POST`. Until the first event that it writes, or the output, an error is a response (`toErrorResponse`): an event that it does not write, as one for another context, decides nothing, and one that it cannot write is a response too, which aborts the signal that went with the DTO. After, an error goes in the stream (`toErrorChunk`), which ends: by default, an event `problem`, as CAITS names its errors, since an `EventSource` gives the name `error` to a connection that fails or ends. An error of the controller as it writes the stream (`toChunk`, `toOutputChunk`, `stateHolds`, the comment of keep-alive) goes in the stream too, and aborts the signal that went with the DTO: the handler stops. An error that `toErrorChunk` cannot write is reported, with the error of `toErrorChunk`. A comment keeps a silent stream alive, and a client that leaves, or stops reading, aborts the signal that went with the DTO. A request that asks for no stream (`streams(dto)`) gets `toResponse(output)` once the handler answers, as from a Controller: an API that streams or not at the same address has one controller. The kernel gives each request the events that its handlers publish (`RequestEvents`), and each context those of all its requests (`ContextEvents`). `@ingenioz-it/caits/messaging/sse` writes the events and the comments: a line of their text ends at `\r\n`, `\r` or `\n`, as the clients read it, and a name or an id with a line break is refused. `controller-extends-controller` takes it. Its presentation test says what the application publishes, and reads the stream: `givenTheApplicationPublishes(…)`, `givenTheApplicationKeepsRunning()`, `expectTheStreamToBe(…)`, `expectTheStreamToStartWith(…)`. In `expectItToSend`, a field of the DTO may be a matcher of Vitest, `expect.any(String)`, for an id that the controller draws. A Controller and a StreamController answer the same errors with the same responses: a controller answers its own errors, and passes the others to `super.toErrorResponse`. Both report with `this.reportError(error)`: a controller that answers an unexpected error in a format of its own reports it too.
- A handler sees its client leave: its `RequestContext` gives `signal`, besides `correlationId`, which aborts when the client of the request leaves. A Controller and a StreamController give the bus the signal of their request with the DTO (`send(dto, { signal })`, the second argument of `MessageBus.send`), and the kernel links it to the request of the handler; a StreamController aborts it too when the client stops reading the stream. A request without a client sees the backend stop: the signal of a turn of a timer aborts as soon as the server stops, a work in the background that the next start runs again; that of a reaction to an event once the grace ends, since it often ends the work of a request. The handler gives the signal to the ports whose work the client waits for, which give it to `fetch` or to their database: the standard way to stop a work whose client left, as the `CancellationToken` of .NET or the `context.Context` of Go. `backend.send(dto, { correlationId, signal })` and `app.send(dto, { signal })` take it. In a presentation test, `expectTheStreamToStartWith` checks, once the client left, that the signal that went with each DTO aborted. The application may import `@ingenioz-it/caits/di/RequestContext` (quality/caits/imports.mjs): in a project whose quality/imports.mjs gives its own list to the application, add it there.
- The container releases what it built: `dispose()` calls `Symbol.asyncDispose`, or `Symbol.dispose`, of each instance that it built, the last built first, so a dependency outlives what needs it. A value given with `.toValue(…)` belongs to whoever made it, and what a parent built to the parent. An adapter that holds a resource (a connection, a child process) releases it this way when the server stops. The backend has `start()` and `stop(requestsDone)`, and `stopBackend()`, from `@ingenioz-it/caits/di/backend`, stops the backend that serves the requests.
- CAITS depends on `compression` and `serve-static`, which the server of `npm start` imports to serve the files, as @marko/run does: a package manager that hoists nothing, as pnpm, would not find them.
- **Breaking**: a controller reads the Request of CAITS, `Request` from `@ingenioz-it/caits/messaging/Request`: its `toDto`, `toResponse` and `toErrorResponse` get it, and `handle` still takes the request of the web, which it wraps. It gives the address, the method, the headers and the signal of the request of the web, and `content({ maxSize })`, the content of the body, which it reads once, at the first call, and gives again at each call. `readBody` and `readForm` are gone: they read a copy of the request (`request.clone()`), which kept the body twice in memory, so that the request stayed readable. The content is the value of the JSON of the body, or the fields of a form, `multipart/form-data` or `application/x-www-form-urlencoded`, as an object, a text or a `File` for each name, a list for a name that comes more than once, each a field of its own as `JSON.parse` makes it: a controller reads both the same way. A browser sends a form from any site without asking the server first, so a form that a browser sends from another site is refused, as its header `Sec-Fetch-Site` says (`cross-site` or `same-site`); a client that is not a browser sends no such header. A body that is neither JSON nor a form is a 415, a body larger than `maxSize` (1 MB by default, from the first call) a 413, a body that is not JSON, or not the form that it says, a 400, and a form from another site a 403 (`CrossSiteRequestError`, `urn:caits:problem:cross-site-request`). The errors of a request live in `@ingenioz-it/caits/messaging/Request`, and `@ingenioz-it/caits/messaging/Controller` still exports them. In a project, import `Request` in each controller (`import type { Request } from "@ingenioz-it/caits/messaging/Request"`), and write `await request.content()` for `await readBody(request)`, `await request.content({ maxSize })` for `await readBody(request, maxSize)`.

### Architecture

- `controllers-read-the-request-of-caits`: a controller reads the Request of CAITS. It names no `Request` that it does not import from `@ingenioz-it/caits/messaging/Request`, nor `globalThis.Request`, and builds no `new Request(…)`: the Request of the web, global, reads its body once only. The facts of a file give the name of each type that it names, qualified or not (`typeReferences`, with `lines.typeReferences`).
- `controllers-built-by-kernel` takes the `AbortController` of the platform, which stops a `fetch`: it is not a controller of the app. Before, an adapter that stopped its requests broke the rule.

### Tests

- The headers that `expectTheResponseToBe`, `expectTheStreamToBe` and `expectTheStreamToStartWith` check take `null` for a header that the response does not have: `{ "retry-after": null }`.
- `givenTheRequest(method, path, body, headers)` sends headers with the request, over the type that its body gives: a controller that reads a header is tested through it.
- `givenTheRequest` sends a `FormData` as a form, `multipart/form-data`, with its files, and `URLSearchParams` as a form of URL encoding, `application/x-www-form-urlencoded`: the presentation test of a controller that reads a form.

### Mutation tests

- **Breaking**: Stryker runs the unit tests in Vitest, which stays started from one mutant to the next (`@stryker-mutator/vitest-runner`): for each mutant, the tests that run its code. Before, each mutant started Vitest again, in a copy of the project, and ran all the tests: at the same number of processes, a use case of a project went from 885 to 108 seconds. A project needs `@stryker-mutator/vitest-runner`, and Stryker 10.1.1 at least, which reads the names of the tests of Vitest 5: `npx caits update` gives the command that installs what package.json lacks. `caits mutation-suite` is gone. Each process of Stryker builds in a folder of its own, `node_modules/.caits/mutation/<number>/`: the Marko plugin empties the entries of the routes in the build folder as a test loads a route, and the processes would empty those of each other.
- A counter stops the code of a mutant that loops without end, whatever the load of the machine. Before, only the clock stopped these loops, and the load of `caits check` slowed past their time mutants that survived, which run the most tests: Stryker counted them as killed, and a score of 100% could hide survivors. `caits mutation` runs again the mutants that the clock still stops, with more time and fewer at once, and their second result counts, in the report and its page: one that runs out of time again loops, and is killed. Its exit code says whether the score, after this second run, is under the threshold `break`.
- A mutant whose tests end in an error that is not a failed test, an error outside the tests or a test runner that stopped, is not judged: Stryker leaves it out of the score, and `caits mutation` fails, with the reason under the mutant. Write the test that sees what it changes. A mutant whose test files fail to load, and nothing else, is killed, as before: its code throws as soon as a test imports it, every time, as a failed test does, where Stryker counts an error outside the tests. It replaces the mutant not tested, whose suite stopped before its tests.
- The mutation tests leave nothing in the temporary folder of the system, which WSL keeps in memory. The tests write their temporary files in a folder of the run (TMPDIR), which goes away at its end; the next run removes the folder of a run that stopped before its end.
- `npx caits update` gives the command that installs the packages that CAITS needs and that package.json lacks.

## 0.7.0

### Architecture

- **Breaking**: `handler-answers-output` reads the return type of `execute`, as the kernel reads the type of its parameter, instead of the names of the classes: each class that it names comes from the DTO file of the use case, and a handler may answer with several (`Promise<MessageAdded | MessageRefused>`). Before, the rule looked for a `new …Output(…)` in the handler. In a project, give each backend `execute` its return type, such as `Promise<AddMessageOutput>`.
- **Breaking**: no rule matches the name of a class with the name of its file. An adapter implements the port of its folder when it imports the interface from `domain/port/<port>/`, under any name, and not when it implements an interface of the same name from elsewhere: `adapter-implements-port`, `infra-folder-implements-port`, `backend-infra-shape` and `adapter-test-runs-contract` find the port in its folder, not by the name of the folder. An event file exports its event under any name (`event-file-exports-its-event`), and `event-type-names-context` reads the name of that class. A domain error lives in `domain/error/<Error>.ts` under any file name (`domain-shape`), as long as its class is an exported `…Error` that extends `Error`. The messages of `domain-file-exports-one-name`, `entity-is-class`, `error-extends-error` and `controller-extends-controller` no longer build a class name from the file. In a project, import the interface of the port in each adapter that implements it.

### Kernel

- **Breaking**: a DTO is a plain class, which extends nothing: `@ingenioz-it/caits/messaging/Input` is gone. The kernel finds the input DTO of a use case in its handler, by the type of the parameter of `execute`: the plugin of the kernel reads it as it reads the ports from the types of a constructor. The `.dto.ts` files are no longer read to find the use cases. A handler whose `execute` names no class is refused when the app starts, with its file. The message bus, `app.send` and the scenarios take any object, and `send` gives `unknown`: compare its output, `expect(await app.send(new GetWordCountQuery())).toEqual(new GetWordCountOutput(3))`, or check its class to read it, `assert(added instanceof AddMessageOutput)`, with the `assert` that the test modules of the backend now give. A controller still says what it sends and what it answers with: `Controller<AddMessageCommand, AddMessageOutput>`. In a project, remove from each input DTO `extends Input<…>`, its import and the `super()` of its constructor; give the `execute` of each handler the type of its input DTO, also when it reads nothing (`execute(_query: ListMessagesQuery)`); and remove `@ingenioz-it/caits/messaging/Input` from `quality/imports.mjs` if it lists it.
- An input DTO that no handler takes gives the same error everywhere, which tells what to write: `No handler takes AddMessageCommand: write one next to its DTO, in <use-case>.handler.ts, with execute(input: AddMessageCommand)`. Before, the message bus said `No handler subscribes to …`, the backend `No context owns …` and the test application of the frontend `No context handles …`. A controller that no context has says where to write it.

### Development

- The build keeps the names of the classes (`keepNames`, in quality/caits/vite.ts): the errors of CAITS name them, and the build numbered a class that has the name of another, as a DTO of the backend and one of the frontend, in the errors of the production server (`No handler takes AddMessageCommand$1`). In a project, run `npx caits update`.

## 0.6.0

### Architecture

- **Breaking**: a use case lives in one folder, from its endpoint to its handler. A context holds its use cases at its root, in `command/` and `query/`: the folders `application/` and, in the backend, `presentation/` are gone. `command/<use-case>/` (or `query/<use-case>/`) holds its DTOs, its handler and its test, `<use-case>.application.test.ts`, and in the backend its controllers, `<use-case>.<name>.controller.ts`, each with its test, `<use-case>.<name>.presentation.test.ts` (`backend-use-case-shape`, `frontend-use-case-shape`): a change of an endpoint touches one folder, a use case goes with its folder, and the name of a test says the layer that it tests. A use case imports nothing from another use case, of its context or of shared (`use-cases-isolated`): what two use cases share lives in the domain. The events of a frontend context are in `event/` (`frontend-event-shape`); its views, its components and its store stay in `presentation/`, since they serve several use cases. The layers stay: the handlers, the DTOs and the events of the frontend are of the application, the controllers and `presentation/` of the presentation (`layer-direction`), so a handler does not import the controller of its use case. The kernel finds the handlers, the DTOs and the controllers in `command/` and `query/`, and the page of the tests groups them by these folders. The rules `backend-application-shape`, `frontend-application-shape` and `backend-presentation-shape` are gone. In a project, move `application/command/` and `application/query/` to `command/` and `query/`, `application/event/` to `event/`, and each controller, `presentation/<use-case>-http/<use-case>-http.controller.ts` and its test, into its use case, as `<use-case>.http.controller.ts` and `<use-case>.http.presentation.test.ts`; rename the test of each use case `<use-case>.application.test.ts`; then change the imports, `#context/application/…` to `#context/…`, the import of the DTO by a controller to `./<use-case>.dto.js`, and the imports of the controllers by the routes.
- The routes hold no logic and no test. The rule `frontend-routes-content` takes in `component/` only the components of Marko and their stylesheets: a module of TypeScript, or a test, goes in a context, where the layers and their tests are. In a project that has some in `src/routes/_frontend/component/`, move them into a frontend context: the code into its layers, and the components that use it into its views. The example keeps the code of its copy buttons and of its theme switch in a frontend context of its own, `site`: its components in the routes only call it.
- The frontend gives its pages in other formats than HTML: a sitemap, a feed, llms.txt. The route of such a document is a folder named after its file, as a page has its folder: `` `sitemap.xml`/+handler.ts `` for `/sitemap.xml`, `` blog/`rss.xml`/+handler.ts `` for `/blog/rss.xml`. Its `+handler.ts` only gives the GET of a view of a frontend context, `export { sitemap as GET } from "#frontend/site/presentation/view/sitemap/sitemap.js";`: the view makes the document from what its context knows, with its test. Before, these documents were files of `public/`, written by hand next to the pages: the frontend routes held no handler, and a handler of `_backend` gives the request to a backend context, which does not read the frontend.
- The presentation of a frontend context holds components, besides its views: `presentation/component/<component>/`, the parts that its views place. A component may take the frontend of its context, publish its events and read its store, as a view does; it imports no view (`components-import-no-view`). A view imports nothing from another view (`views-import-no-view`): what views share is a component. In a project where a view imports the files of another, move them into a component.
- A frontend context may have no store: a context without a use case, whose views and components publish events and read no state. Its frontend is its bus. A context with use cases and no store is refused, since the store sends their input DTOs. `testPresentation` gives no store for such a context, and records in `published` every event of the bus: a test reads the events that a view or a component publishes.
- The contexts talk through the context shared, in the backend as in the frontend: the context map of a context shares an event of the context as an event of shared, on the shared bus, and the context map of each context that hears it turns it into what the context reacts to. A context and its context map name only their own context and the context shared: two contexts never name each other.
  - Each context has its context map, `src/<side>/<context>/context-map.ts`, beside its di.ts. It translates both ways. `share(SomeEvent, event => [new SharedEvent(…)])` turns an event of the context into events of shared, on the shared bus: in the backend, an event that a handler published; in the frontend, one that a view, a component or a handler published on the bus of the context. `when(SharedEvent, event => […])` turns an event of shared into what the context reacts to: in the backend (`@ingenioz-it/caits/messaging/ContextMap`), input DTOs of the context, which its handlers execute (a line that gives the input of another context is reported, and sends nothing); in the frontend (`@ingenioz-it/caits/messaging/FrontendContextMap`), events of the context, on its own bus, which its store reads. The event of the context holds what the events of shared need: the map reads no state. The test of a map reads what its lines give: `inputsFor` and `eventsFor` of the `ContextMap` in the backend (`@ingenioz-it/caits/testing/backend/context-map`), `eventsFor` in the frontend (`@ingenioz-it/caits/testing/frontend/context-map`).
  - **Breaking**: in the backend, a handler publishes the events of its context, and no longer those of shared. An event that the context map does not share stays in its context. In a project where a handler publishes an event of shared, give its context an event of its own, `domain/event/`, publish it, and share it in the context map: `share(NoteAdded, event => [new NotePosted(event.id)])`. The handlers of the context shared still publish its events on the shared bus. The application test of a handler (`createTestApplication`, `applicationScenario`) reads the events of its context, and the test of a flow (`backendTest`) the events of shared: `subscribeToContexts` of the backend watches the first, `subscribe` the second.
  - In the frontend, the bus of the context shared is the shared bus of a $global (one request on the server, one page in the browser). A context that hears an event of shared is built if no view asked for it yet, and the frontend of shared when a context first shares an event. The components of shared publish its events on its own bus, the shared bus. A context without a store tells the other contexts as well: its map shares the events that its views publish.
  - A view or a component takes only the frontend of its context (`views-take-own-frontend`), and in a context other than shared, only the context map imports the events of shared, in the backend as in the frontend (`shared-events-in-map`): the handlers, the entities, the controllers, the store, the views and the components name only the events of their context. A test may import them. The test of a view reads in `published` the event of the context that it publishes, and the test of the map what the map shares.
  - The rules read the lines of the context maps. A map has one export, the list of its lines, made with the `when` and the `share` of the kernel for its side (`context-map-holds-lines`). Each line goes one way (`context-map-line-direction`): `share` starts from an event of its context and gives events of shared, `when` starts from an event of shared and gives what its context reacts to. A line that goes the other way never starts, and its test passes all the same. In the frontend, the maps make no cycle of events, in one map or across several (`context-maps-without-cycle`): the buses carry an event at once, and a cycle would never end.
  - The lint keeps a context map a translation (quality/caits/eslint.js): it reads neither the clock (`Date.now()`, `new Date()`), nor chance (`Math.random()`, `crypto`), nor the page or the process (`window`, `document`, `localStorage`, `fetch`, `process`…), and keeps no state (no `let` at the top of the file). The event that it translates holds what the new events need.
  - A context map imports only the events of its context and of shared, the input DTOs of its context in the backend, and the values of the domain (`context-map-translates-shared`). No layer imports it: the kernel reads it (`layer-direction`). The context shared has none (`shared-hears-no-context`).
  - **Breaking**: the context map of the backend, `src/backend/context-map.ts`, is gone, and with it the rules `context-map-reads-events-and-dtos`, `context-map-without-routes` and `routes-without-context-map`; `src/backend` holds only the contexts, and the integration tests of the whole backend (`*.integration.test.ts`). In a project that has one, move each event that a context hears into the backend context shared (`domain/event/`), and each line of the map into the context map of the context that reacts.
- The frontend has a context shared, `src/frontend/shared/`, as the backend has: a context as the others, with its di.ts, and its store if it needs one, that every context of the frontend may import. The contexts import its files with the shortcut `#frontend-shared/`, which the plugin of the kernel gives Vite and quality/caits/tsconfig.json gives TypeScript (`#shared/` stays the backend context shared). They place its components by their tag, `<badge>`, and do not import their file (`shared-components-placed-by-tag`): Marko reads the import of a template from the package.json of the context, whose shortcuts lead only into it, and would not build it. A component of shared is a Marko tag, `component/<name>/index.marko`, and `src/frontend/marko.json` gives Marko the folder of these tags, `{ "tags-dir": "./shared/presentation/component" }` (`shared-components-are-tags`: write it with the first component of shared).
- **Breaking**: no test crosses contexts (`tests-in-one-context`). A test in a context reads only its context and the context shared of its side; a test out of the contexts (`src/backend/*.integration.test.ts`, `test/`) reads one context at most; a test of the frontend builds only the frontend of its context, with `testPresentation`. Each context is tested alone, and its context map on its own lines. Before, the rules on imports read only the production code. In a project where a test crosses contexts, split it: in the first context, test what its context map shares; in the second, what it does with that event of shared.
- **Breaking**: the code turns off no check (`exceptions-in-quality`). No comment turns off a rule of ESLint (`eslint-disable…`), an error of TypeScript (`@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`), lines of the coverage (`v8 ignore`, `c8 ignore`, `istanbul ignore`) or mutants (`Stryker disable`), and no test is kept from running or from failing (`skip`, `skipIf`, `runIf`, `only`, `fails`, `fail`, `fixme`). The rule reads the tests and the Marko templates too, which ESLint does not read, and ESLint ignores such a comment as well (`noInlineConfig`). An exception lives in quality/, as narrow as it can be: a rule of ESLint turned off for one file in quality/eslint.config.js, a file out of the coverage in quality/vite.config.ts, a file out of the mutants in quality/stryker.config.mjs, a rule of quality/architecture.mjs that leaves one file aside. In a project with such a comment, move the exception into quality/. The rules of a project read the comments of each file (`comments`), and the name that a call starts from (`root` of each call: `test` for `test.skip(…)`).
- The architecture check reads a tag that Marko finds without an import (in a folder of tags) from the root of the project: the rules on the direction of the imports read it, and `imports-by-shortcut` no longer takes it for an import that goes up a folder.
- **Breaking**: `caits architecture` prints each violation as `<file>[:<line>] [<rule>] <message>`: the file, the line of the construct that breaks the rule when the rule points at one (the import, the export, the class, the call, the comment…), the rule, then the message. It no longer prints `→ <target>`: when the target of an import matters, the message names it. Each message says what is wrong, in full sentences, then how to fix it, with the names that the rule knows: the files, the classes, the port of an adapter, the contexts, the use cases, the name or the path to give. `src/backend/messages/command/add-message/add-message.handler.ts:2 [application-imports-no-infra] The application layer must not import the infra layer (src/backend/messages/infra/message-repository/file-message-repository.js). Depend on its port, MessageRepository (src/backend/messages/domain/port/message-repository/MessageRepository.ts), instead, and bind the adapter in src/backend/messages/di.ts.` The last line stays: `1 architecture violation.`
- **Breaking**: `layer-direction` is gone. One rule per pair of layers says what it forbids, and how to fix it: `domain-imports-no-application`, `domain-imports-no-presentation`, `domain-imports-no-infra`, `application-imports-no-presentation`, `application-imports-no-infra`, `presentation-imports-no-infra`, `infra-imports-no-presentation`, `infra-imports-no-application` (the backend only: the infra of the frontend may import its application), `di-imports-no-application` and `di-imports-no-presentation`. `context-map-read-by-kernel` says that no layer imports a context map. A context map that imports the presentation or the infra breaks `context-map-translates-shared` only: before, it broke `layer-direction` too. In a project whose quality/architecture.mjs removes, replaces or changes `layer-direction`, do it to the new rules.
- **Breaking**: three rules have a new name, and the same check: `no-test-environment` is `production-imports-no-test-environment`, `no-test-support` is `production-imports-no-test-support`, and `nothing-outside-src` is `production-imports-only-src`. In a project whose quality/architecture.mjs names them, rename them.
- **Breaking**: the packages that each layer imports are lists, in `quality/imports.mjs`. An entry is a package (`uuid`), a module (`@ingenioz-it/caits/Token`), a Node API (`node:crypto`), or a folder of modules (`@ingenioz-it/caits/messaging/*`); a layer without a list imports any package. The lists of CAITS, in `quality/caits/imports.mjs`, close the domain and the application: the domain imports `@ingenioz-it/caits/Result`, `/Token` and `/DomainEvent`, the application these, `@ingenioz-it/caits/messaging/Input` and `/EventPublisher`; the presentation, the infra, di.ts and the context map have no list. `domain-imports-only-listed-packages` and `application-imports-only-listed-packages` replace `core-without-node` and `domain-uses-kernel-primitives`: before, a package of npm passed in the domain, and only the Node APIs did not. `presentation-imports-only-listed-packages`, `infra-imports-only-listed-packages`, `di-imports-only-listed-packages` and `context-map-imports-only-listed-packages` check the layers that a project gives a list. `quality/imports.mjs` belongs to the project: `caits init` writes it, with the lists of `quality/caits/imports.mjs`, and `caits update` never writes it. Without it, the lists of CAITS apply. In a project where the domain or the application imports a package, list it in `quality/imports.mjs` (`export default { ...allowed, domain: [...allowed.domain, "uuid"] }`), or move the code behind a port.
- `zod-in-presentation` and `marko-in-frontend-presentation` read only the layers without a list: in a layer with a list, the list says it, and one import breaks one rule. The infra of the frontend may import zod, to check the data that it receives. `marko-in-frontend-presentation` leaves an import of a template of the frontend presentation to the rules on the layers and the sides.
- The rules point at lines, and read the project on the imports too. The facts of a file give the line of each construct: `line` on each export, class, property of a class, call, name imported and item of `export default [ … ]`, and `lines`, with the line of each import, `new`, `type: "…"` of an object, tag and comment, in the order of `imports`, `constructed`, `objectTypes`, `tags` and `comments`. A check gives a message, `{ line, message }`, or a list of both; a rule on the project gives `{ file, line?, message }`. A rule on the imports gets the project as its second argument, as a rule on the files does, and the line of the import (`link.line`), where its message goes unless it gives another line. The project holds the lists of quality/imports.mjs: `packages`. `checkArchitecture(root, sources, rules, packages)` takes them, and a violation has a `line`, but no longer a `subject`. The rules of a project keep working: a message that is a text still is one.
- In a project, run `npm install --save-dev @ingenioz-it/caits@latest` (`npm update` stays in 0.5.x) and `npx caits update`. The AGENTS.md of a new project says where the use cases go, where these routes go, that the routes hold no test, where the components and the context shared of the frontend go: in a project made before, take its lines on the contexts, the use cases, the frontend and `src/routes/`.

### Kernel

- The kernel refuses, when it starts, a di.ts that gives something other than a binding: before, it lost it without a word. The empty di.ts of a context shared that holds only events, `export default [];`, thus passes the mutation tests. It refuses as well a context map that is not a list of lines, or a line of the other side: a `when` of the backend in a map of the frontend.

### Development

- `npm run dev` keeps working while `npm run check` runs. The development server watched the sandbox of Stryker, `.stryker-tmp/`, which holds a copy of the project: each copy of its tsconfig.json made the server empty its cache, until its pages lost their scripts and their styles. In a project, run `npx caits update`.
- `npx caits update` writes only the defaults that change, and removes those that CAITS no longer gives. Before, it wrote them all again: a development server that watched them (vite.ts, tsconfig.json) restarted at each update, and could lose the dependencies that it optimized.
- The outputs of `caits` have colors in a terminal, and none in a pipe or a file: an AI agent reads no code of color. `caits check`: the list of the checks dim, `✓` green, `✗` red, each duration dim, the header of a failed check bold, and the last line green or red; in a terminal, it runs the checks with FORCE_COLOR, so that the output of a failed check keeps the colors of its tool, and in a pipe with NO_COLOR. `caits architecture`: the file and its line cyan, the rule dim, the count of the violations red. `caits mutation-summary`: the scores green when every mutant is killed, else red, the paths cyan, and for each survivor its line dim, its status red and its mutator yellow. The errors are red, the warnings yellow, and the next steps of `caits init` give their commands in cyan. NO_COLOR turns the colors off, FORCE_COLOR turns them on.

### Mutation tests

- Only a test kills a mutant. Before, the suites that Stryker runs at once shared the caches of Vite and Vitest, in node_modules/: each suite wrote them again, since they depend on the folder of its copy, and two suites could clash there. Vitest then stopped before the tests, and Stryker counted the mutant as killed: a mutant that survives could pass unseen, with a score of 100%. Each suite now keeps its caches in its copy, and shares only the packages. The mutation tests of the example take about 6 seconds more: the suites no longer share which test file failed last, which Vitest runs first.
- A suite that stops before its tests says so: `The unit tests did not run`. Stryker counts the mutant as killed all the same, as for any failed suite; `caits mutation-summary` counts it as not tested and lists it, and `npm run test:mutation` fails. Run it again.
- A suite that Stryker stops for taking too long leaves no copy in the temporary folder: Stryker stops it with SIGKILL, and the next suite removes the copy. Before, each mutant that timed out left one.

## 0.5.1

### Command

- `npm run test:mutation` gives the mutants that survived when the score is under 100%. It runs `caits mutation`: Stryker, then the score of each file and the survivors, whether Stryker passed or not, with the exit code of Stryker. Before, the script stopped after Stryker when it failed, and its summary showed only when every mutant was killed. A run that stops before its report shows no summary of the run before.

## 0.5.0

### Development

- `npm run tdd` is plain watch mode (`vitest --config quality/vite.config.ts`): it runs the unit tests, then at each save the tests of the changed files. Before, it ran no test when no file differed from the last commit, or out of a git repository. `init` no longer writes the script `test:watch`, which was the same.
- In watch mode and in the development server, a new handler, DTO, controller, di.ts, store or context map is found at once: no restart of Vitest or of the server. Before, the tests failed with `No context owns …`.
- `npm run lint:code` passes on a new project or a new clone: the ESLint configuration of CAITS (quality/caits/eslint.js) writes the types of the routes (.marko-run/routes.d.ts) first. Before, the lint failed when no build, test or development server had written them.

### End-to-end tests

- `caits e2e` refuses to run when the port of the server is in use (`Port 4310 is in use: a server runs at http://127.0.0.1:4310/ already. Stop it, then run the end-to-end tests again.`): before, it ran the tests on that server, which could be the build of another project.
- `caits e2e` stops the server, Playwright and its browsers also on Ctrl+C (exit code 130) and SIGTERM (143), and waits for the server as long as `webServer.timeout` says (120 s when it says nothing).
- The folder of the data of the end-to-end server (DATA_DIR) has a name for each path of project: two projects with the same folder name no longer share it. `caits e2e` empties it before it starts the server; the global setup of Playwright that emptied it again (quality/e2e-setup.mjs) is removed.

### Kernel

- `readBody` reads only a body that says it is JSON (`content-type: application/json`, or a type with the suffix `+json`): else the Controller answers 415 `urn:caits:problem:unsupported-media-type`. A browser sends a body of another type from any site without asking the server first. A body larger than 1 MB (`MAX_BODY_SIZE`, or the size that the second argument gives) gets 413 `urn:caits:problem:request-body-too-large`.
- `presentationScenario(app).givenTheRequest(method, path, body)` sends each body with `content-type: application/json`, also a body that is a string.

### Command

- The AGENTS.md of a new project says that, in an AI agent, `npm run tdd` runs the unit tests once and stops: Vitest does not watch there.
- `caits --version` gives the version. `caits <command> --help` gives the usage.
- An unknown command or option, an option without its value, or an argument too many gives a short message and ``Run `caits --help`.``, with the exit code 1, in place of a stack trace. So do `caits architecture` without quality/architecture.mjs and `caits mutation-summary` without a report.
- `caits update` takes no argument: `caits update --help` no longer writes quality/caits/.
- `init` reads the package.json of the project before it writes a file, and names the file when it is not valid JSON. It says when git, npm or npx is not installed. It refuses an example with a symbolic link. Its next steps put a folder with a space in quotes.
- `caits check` exits with 143 on SIGTERM, and `caits mutation-suite` with 130 on SIGINT.
- `caits architecture` writes `1 architecture violation.` and `2 architecture violations.`, not `violation(s)`.

### Package

- CAITS is on npm, as the package `@ingenioz-it/caits`: `npx @ingenioz-it/caits init my-app --example` makes a project, and a project depends on `@ingenioz-it/caits` `^0.5.0` in place of the git tag of GitHub. Its imports start with `@ingenioz-it/caits/` in place of `@ingeniozit/caits/`: in a project, replace the name in package.json and in the imports, then run `npm install` and `npx caits update`. npm refuses the name `caits`, too close to the names of other packages.
- git is necessary only for `init --example`, which gets the example with git.
- Node.js 22.18 or later is necessary in Node 22 (`^22.18.0 || ^24.0.0 || >=26.0.0`): from 22.18, Node strips the types of TypeScript without an option.
- The peer dependencies give the versions that CAITS supports: `@marko/run` `^0.11.13`, `vite` `^8.0.0`, `vitest` `^5.0.0`, and the packages that the defaults of CAITS import (`@marko/compiler`, `@playwright/test`, `@eslint/js`, `typescript-eslint`). package.json has a homepage, a page for the issues, an author and keywords.
- The type check and the lint of CAITS also read the tools of quality/.
